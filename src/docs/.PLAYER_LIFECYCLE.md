# Player Character Lifecycle

Documents the full arc of a `Player` object from the moment someone joins a game to the end of
the epilogue. Covers both Dungeon Mode and Town Mode where they differ.

---

## 1 — Joining & Initial State

A player joins by entering a game code in the player-client. On creation a `Player` is initialized
with:

- `authorId` — random UUID, the player's stable identity throughout the game
- `userName` — the name they typed
- `joinedAt` — timestamp used for all phase-assignment offset calculations (sort order = join order)
- Seven base stats, all set to **4**: `strength`, `dexterity`, `charisma`, `intellect`, `wealth`,
  `magic`, `favor`
- Empty `traits: []`, `titles: []`
- `playerClass: null` (until they select one)

---

## 2 — Character Creation (INIT)

Shown via the `player` component in the player-client. Two steps completed before the game begins:

### Step 1 — Class Selection

`GET /player/classes` returns all four `PlayerClassOption` values. The player picks one:

| Class | What it unlocks |
|---|---|
| **Bard** | Can spread outcomes to all players (`ALL_PLAYERS`) |
| **Herald** | Can give titles to other players (`TITLE`) |
| **Scribe** | Can give traits to other players (`TRAIT`) |
| **Fabulist** | Can convert encounters into companion traits (`COMPANION`) |

Stored on `Player.playerClass`. Gates which repercussion types appear in the `repercussion-toggle`
component during writing phases. Class does not change over the course of the game.

### Step 2 — Trait Selection

Player picks one starting trait from the available `Trait[]` pool. Appended to `Player.traits`
as `TraitType.STANDARD`.

### displayName

`Player.getDisplayName()` is computed, not stored: `userName` + any `TraitType.TITLE` traits
joined with commas. Example: "Morwen, The Unbroken, Voice of the Vale".

---

## 3 — PREAMBLE

Static text establishes the narrative stakes for all players — where they are, what is coming,
and what the journey will demand of them. No player input is required; this is a read-only
information phase shown on the shared game-client screen.

---

## 4 — Tutorial Round Zero (roundNumber = 0)

Before the first writing round, players experience a pre-authored tutorial. This uses the normal
LOCATION_VOTING → NAVIGATE_WINNER flow but with starting locations and pre-written stories.

### Starting Location Selection

`initializeLocationVoting` filters to `Location.startingLocation == true` entries only (in round 0).
Players vote just as in regular location voting. `Player.selectedLocationId` and location traits
are set via the normal `handleLocationVoting` + `handleLocationTraits` flow.

### handleRoundZeroBoard

When `roundNumber == 0`, the SET_ENCOUNTERS state machine intercept calls `handleRoundZeroBoard`
instead of entering writing phases:

- For each player (sorted by joinedAt): find their selected `Location`
- Pick `location.startingStories[0]` for the first player at that location, `startingStories[1]`
  for subsequent players (capped at last index)
- Clone the story with a new storyId, assign `authorId = player.authorId`, place on GameBoard
- Partners are skipped in round 0 (NAVIGATE_WINNER goes directly to MAKE_CHOICE_VOTING)

### DESTINY Trait Award

Starting stories have exactly one `OutcomeFork` per `Option`. That fork carries `Repercussion`
objects with `repercussionType = RepercussionType.DESTINY`. Because there is only one fork, the
existing single-fork auto-select path in `MAKE_OUTCOME_CHOICE_VOTING` fires automatically.

`handleRepercussions` checks for DESTINY type and creates `Trait(TraitType.DESTINY)` — a gold-
colored trait (color `#FFD700`) appended to `Player.traits`. This is the player's Destiny.

After all encounters in round 0 resolve, `roundNumber` increments to 1 and the game loops back
to `PREAMBLE_AGAIN` for the first real writing round.

---

## 5 — Location Selection (LOCATION_VOTING, locationVoting mode, rounds 1+)

Players vote on where they will travel next. Candidates come from `AdventureMap.locations`
filtered to `startingLocation == false` (starting locations are excluded from regular rounds).

`initializeLocationVoting`:
- Filters `AdventureMap.locations` to non-starting locations
- Shuffles randomly, selects N (N = player count)
- Creates one `TextSubmission` per location in the LOCATION_VOTING phase

Each player independently votes for one location. Votes are individual — different players can
choose different locations and will end up on separate paths through the dungeon.

`handleLocationVoting` (fires on resolution):
- Reads each player's vote and sets `Player.selectedLocationId` to the `Location.id` they chose
- Immediately calls `handleLocationTraits`:
  - Each player receives all `Trait[]` defined on their chosen `Location` object
  - These are appended to `Player.traits` — the location visit is permanently recorded on the
    character before they've written or resolved a single encounter

---

## 5 — Encounter Writing (SET_ENCOUNTERS → WHAT_HAPPENS_HERE)

### SET_ENCOUNTERS

Players are assigned a location by join-order offset and name encounter labels for it. For
example, if assigned "A Tavern in the Woods", a player might write:
- "Drunk Bar Patrons"
- "A Strange Mapmaker"

These become `EncounterLabel` objects on `AdventureMap.encounterLabels[]`, tagged with the
`locationId` of the location they were written for.

### WHAT_HAPPENS_HERE

Players are assigned an `EncounterLabel` written by someone else (offset) and write the full
scene description (`Story.prompt`). The story is placed as an `Encounter` on the `GameBoard`
at coordinates `(currentX + i, y)` and carries `playerIds` — the list of players assigned to
this encounter (used to target repercussions later). `Story.roundNumber` is also set here
(`gameSession.getRoundNumber()`), primarily to distinguish a real round-1+ story from a round-0
tutorial story sharing the same `authorId` — the latter predates the field and defaults to `-1`.

Players who selected the same location as the encounter's origin location will be the ones who
encounter it during MAKE_CHOICE_VOTING.

Like `HOW_DOES_THIS_RESOLVE` below, a player writing (or branching onto someone else's) encounter
here may also attach a `Repercussion` — `getPlayerRepercussionTypes` isn't phase-gated. One
attached this early lands on `Story.repercussions` (not any `OutcomeFork` — none exist yet) and
later gets combined with the winning `HOW_DOES_THIS_RESOLVE` fork's own repercussions when that
story resolves; see `.CLASSES.md`, "WHAT_HAPPENS_HERE-time repercussions stack with the winning
fork's own," for the full mechanic.

`story.playerIds` always ends up containing the "distribution-assigned" player for this story —
whichever player the same offset-based assignment used elsewhere (`getPlayerAssignment`) maps the
original author to — appended unconditionally after any location-scoping logic runs, regardless of
that player's actual location. This is why `story.playerIds` is never an *exact* location-scoped
set, only "every same-location player, plus possibly one more."

### WHAT_CAN_WE_TRY

Player is assigned 1–2 stories by offset and proposes action options for each.
Winning options become `Option` objects on the story. The player assigned to propose/resolve a
given story (the "resolver") is not necessarily the same player who authored it during
`WHAT_HAPPENS_HERE` — both are independently derived from the same offset-based assignment, but
starting from different players, so they only coincide by chance.

### HOW_DOES_THIS_RESOLVE / HOW_DOES_THIS_RESOLVE_AGAIN

Player is assigned one story and writes the resolution for one of its options. This is where
**player class matters**: when making a text addition the player may attach a `Repercussion`
from the types their class unlocks:

```
TextAddition {
  authorId,
  addedText,
  repercussion: { repercussionType, repercussionSubmission }
}
```

A submission here can be a fresh root (`submissionId: null`) or a **branch** onto an existing
submission (`submissionId` set to the parent) — the real player-client surfaces other players'
submissions to branch onto via `GET /collaborativeText/available`
(`CollaborativeTextHelper.getAvailableSubmissionsForPlayer`), which excludes the requester's own
submissions, so branching is always onto someone else's text. This is also how a second
`OutcomeFork` gets created on one `Option`: two different players each branching a sibling addition
directly onto the *same* root produce two leaf submissions, both attributed to that option — see
`.OUTCOMES.md`, "How a second `OutcomeFork` actually forms" for the full mechanism
(`CollaborativeTextHelper.createBranchedSubmission` / `getSubmissionsWithoutParentSubmissions`).
Branching a **chain** instead (B branches onto A's addition, not onto the root) accumulates
repercussions from every addition in that chain onto one fork — see `.CLASSES.md`, "Repercussion
resolution on winner calculation" for what happens when such a fork wins.

Repercussions attached during this phase aren't resolved into real effects yet — that only happens
once `MAKE_OUTCOME_CHOICE_VOTING` picks a winning fork (see below).

## 6 — Individual Encounter Resolution (per player, per encounter)

After the writing phases conclude, each player takes a turn resolving the encounter that was
written for them. The encounter resolution loop runs one player at a time.

### MAKE_PARTNER_CHOICE_VOTING

Before their encounter begins, a player may choose to partner with another player. This is a
two-step mutual opt-in:

1. **MAKE_PARTNER_CHOICE_VOTING** — The active player votes for a partner from the available
   player list. The "winner" is whichever player received the most votes.
2. **ACCEPT_PARTNER_CHOICE_VOTING** — The chosen player votes to accept or decline.

`handleAcceptPartnerChoiceVoting`: If accepted, the partner's `authorId` is added to
`Story.partnerIds[]` on the active player's story. The relationship is mutual — the active
player's `authorId` is also added to the partner's story at the same location.

**Partners vote in both MAKE_CHOICE_VOTING and MAKE_OUTCOME_CHOICE_VOTING** alongside the
primary player. They also share in any repercussions that result from the encounter outcome.

### MAKE_CHOICE_VOTING

The active player (and any partners) vote on which `Option` to pursue.
→ `Story.selectedOptionId` is set to the winning vote.

### MAKE_OUTCOME_CHOICE_VOTING

If the chosen option has multiple `OutcomeFork` submissions, all other players vote on which
fork applies — deciding the active player's fate. If only one fork exists, it is selected
automatically (`GameSessionHelper` skips real voting whenever `outcomeForks.size() < 2`).
→ `Option.selectedForkId` is set (**not** `selectedOutcomeForkId` — that name doesn't exist on the
model); repercussion resolution fires immediately.

### Repercussion Resolution

`handleRepercussions` fires when `MAKE_OUTCOME_CHOICE_VOTING` resolves, reading every repercussion
off the **winning fork's full addition chain** (not just its final addition — see the branching
note under HOW_DOES_THIS_RESOLVE above):

```
Target players = story.playerIds + story.partnerIds

TRAIT     → new Trait(repercussionSubmission, TraitType.STANDARD) appended to each target
TITLE     → new Trait(repercussionSubmission, TraitType.TITLE) appended — surfaces in displayName
COMPANION → new Trait(story.encounterLabel.encounterLabel, TraitType.COMPANION) appended — the
            LABEL always comes from the story's own encounter label, never from whatever text was
            submitted as repercussionSubmission (the server ignores it for this type)
ALL_PLAYERS → whichever of the above are ALSO present on the same winning fork's addition chain
              get applied to every player in the game instead of just targets. ALL_PLAYERS alone,
              with nothing else in the chain, has nothing to spread - no Trait is created.
```

A round-1 story whose winning fork carries **no** repercission other than possibly a lone
`ALL_PLAYERS` gets offered back to its author in round 2 as a "prequel" — see "Prequel stories" at
the end of this section. This is the real "unfinished business carries forward" mechanic; despite
what older notes in this doc said, it is **not** a `RepercussionType.SEQUEL` effect — that type is
dead code (see `.CLASSES.md`).

### NAVIGATE_WINNER

`PlayerCoordinates.x++`. Encounter resolution repeats for the next encounter in the round. When
all encounters are done:
- `roundNumber < 2` → increment round, loop back to WHAT_HAPPENS_HERE (writing rounds are 1 and 2)
- `roundNumber >= 2` → proceed to ENDING_PREAMBLE → DEFINING_TRAITS_VOTING → WRITE_EPILOGUES

### Prequel stories — round 2's real callback mechanic

When round 2's `WHAT_HAPPENS_HERE` starts, `CollaborativeTextHelper.getOutcomeTypes` re-offers a
round-1 story back to the same player who **authored** it (not whoever resolved it), *if* that
story is `visited` and its winning fork carried no repercussion other than possibly a lone
`ALL_PLAYERS` (`hasNonSpreadRepercussions`, `CollaborativeTextHelper.java`) — i.e. nothing gave that
encounter narrative weight the first time around. The offer is injected as the first `subType` of
the player's location-wrapped `WHAT_HAPPENS_HERE` outcome types (under the `locationVoting` flag —
see `.OUTCOMES.md`), carrying `clarifier = <the original story's storyId>` so the client can look up
and display the prequel content. There is no cap on how many round-1 stories a single author can
have offered back this way — it's a filter, not a "pick one" selection.

This is the mechanic that actually delivers on "an unresolved encounter carries into round 2" — the
`RepercussionType.SEQUEL` enum value some earlier design intended for this purpose was never wired
up (see `.CLASSES.md`, "SEQUEL is unused"). A story that instead resolved with a real `TRAIT`,
`TITLE`, `COMPANION`, or `ALL_PLAYERS`-plus-something repercussion is **not** re-offered — it's
considered narratively resolved.

When the resulting round-2 "sequel" story (`Story.prequelStoryId` set) is created in
`handleWhatHappensHereStreamlined`, its `playerIds` are scoped to only the players at the sequel
story's **own** location (`getPlayersAtStoryLocation`, falling back to all players if the sequel
has no location), not every player in the game — matching how `handleSpread` also scopes a Trait's
`ALL_PLAYERS` companion effect to players at the originating story's location (see "Repercussion
attachment and resolution" above / `.CLASSES.md`). Verified against the live backend via
`FullGameSequelLocationScopeTest` (`src/integrationTest`), which forces a genuine round-2 location
split so the scoped set is a proper subset of all players, not coincidentally identical to it.

## 7 — Town Mode Stat Phases (Town Mode only)

Town Mode adds world-building phases that create shared stat types used in adventure resolution:

| Phase | Effect |
|---|---|
| `WHAT_DO_WE_FEAR` | Winning submission becomes a `StatType` (the fear entity) on `AdventureMap.statTypes` |
| `WHAT_ARE_WE_CAPABLE_OF` | Top 6 winning submissions become `StatType[]` on `AdventureMap.statTypes` |

The base player stats (strength, dexterity, charisma, intellect, wealth, magic, favor — all
initialized to 4) are checked against the relevant `StatType` to determine success or failure.

---

## 8 — Defining Traits (DEFINING_TRAITS_VOTING)

Before epilogues are written, each player selects the defining moments of their character's arc.

`getOutcomeTypes(DEFINING_TRAITS_VOTING)` returns the requesting player's own `traits[]` as
OutcomeTypes (each with `clarifier = selectedLocationId` as a fallback source context).

The player submits ONE TextSubmission encoding two picks:
- `outcomeTypeWithLabel` = the DEFINING trait (what defined their journey)
- `outcomeTypeWithLabel.subTypes[0]` = the PRICE trait (what they sacrificed)

`handleDefiningTraitsInternal` reads these and writes to `Player.definingTraits`:
```
Player.definingTraits = [
  DefiningTrait { traitName, category="TRAIT", type="DEFINING", sourceStoryId=clarifier },
  DefiningTrait { traitName, category="TRAIT", type="PRICE",    sourceStoryId=clarifier }
]
```

---

## 9 — Epilogue (WRITE_EPILOGUES)

Each player is assigned another player's character arc by join-order offset (`index - offset`).

`getOutcomeTypes(WRITE_EPILOGUES)` now returns the assigned player's `definingTraits` as subTypes
(instead of all visited stories). If no definingTraits are set, falls back to visited stories.

The epilogue author:
1. Selects a defining trait as the OutcomeType context for their writing
2. Writes how that character's story concluded
3. Marks whether they achieved their destiny (toggle → `TextSubmission.outcomeType = "DESTINY_ACHIEVED"`)

`handleEpilogues` sets `Ending.didWeSucceed = true/false` based on the destiny toggle. The winning
epilogue text is attached to that player's record as an `Ending`.

Only DESTINY-typed traits (gold `#FFD700`) are shown as context badges above the writing area,
keeping the focus on the player's core narrative identity.

---

## 10 — Final Player State

By the end of the game a player's record holds:

| Field | What it reflects |
|---|---|
| `playerClass` | The class chosen at creation — unchanged throughout |
| `traits[]` | Starting trait + location traits + DESTINY trait (from tutorial) + TRAIT/COMPANION/TITLE repercussions from encounter resolution |
| `definingTraits[]` | Two DefiningTrait entries: one DEFINING, one PRICE — chosen by the player in DEFINING_TRAITS_VOTING |
| `titles[]` | Separate list of title strings (mirrors TITLE-type traits - legacy) |
| `displayName` | `userName` + all TITLE traits joined with commas |
| `selectedLocationId` | The location they voted for in round 0 (tutorial) or round 1 |
| `playerCoordinates` | Final position on the dungeon grid |
| Base stats | Initialized at 4; modified by adventure outcomes in Town Mode |
