# Player Classes & Repercussions Reference

## Overview

Player classes gate which **repercussion types** a player can attach to their text additions during
collaborative writing phases. A player's class is chosen during setup and stored as a
`PlayerClassOption` on their `Player` object.

---

## Player Classes

| Class | Description | Unlocked RepercussionType |
|---|---|---|
| **Bard** | Spreads story outcomes to all players, including yourself | `ALL_PLAYERS` |
| **Herald** | Gives new titles to other players | `TITLE` |
| **Scribe** | Records histories and adds traits to other players | `TRAIT` |
| **Fabulist** | Converts encounters players survive into companion traits | `COMPANION` |

Defined in `model/PlayerClass.java` (enum). Serialized to the client as `PlayerClassOption`
(a plain class with the same fields) via `GET /player/classes`.

---

## Repercussion Types

| Type | Color | Effect |
|---|---|---|
| `TRAIT` | `#0288d1` (blue) | Gives a named trait to players at the story's encounter |
| `TITLE` | `#7b1fa2` (purple) | Gives a title; appended to `Player.displayName` |
| `COMPANION` | `#E60000` (red) | Converts the encounter label into a companion trait on those players |
| `ALL_PLAYERS` | `#f57c00` (orange) | Spreads TRAIT/TITLE/COMPANION effects to every player, not just encounter players |
| `SEQUEL` | `#388e3c` (green) | **Dead code — never produced by any code path.** See "SEQUEL is unused; the real callback mechanic is prequel stories" below before building anything on it. |

Defined in `model/RepercussionType.java` (enum). Each type carries: `name`, `label` (input prompt
text), `instruction` (toggle-off description), `description` (toggle-on description), `color`.

### SEQUEL is unused; the real callback mechanic is prequel stories

`SEQUEL` is declared in the enum but **no `PlayerClass` unlocks it** (`model/PlayerClass.java` —
Bard/Herald/Scribe/Fabulist only grant ALL_PLAYERS/TITLE/TRAIT/COMPANION respectively) and nothing
in `helper/CollaborativeTextHelper.java` ever constructs a `Repercussion` with this type. Confirmed
2026-08-09/10 while building integration test coverage for every repercussion type
(`nowhere_java/src/integrationTest/`) — grepping the whole `src/main/java` tree for `SEQUEL` turns
up nothing that produces one.

There *is* a block in `handleRepercussions` (`CollaborativeTextHelper.java`, guarded by
`repercussions.isEmpty() && roundNumber < 2`) that looks like it should be the "no one chose a
repercission, so this encounter carries over" default — but it's unreachable: its only call site is
itself gated by `if (!repercussions.isEmpty())`, so the empty-list branch inside it can never run.
Even if it somehow ran, it only appends a cosmetically-broken outcome-display string
(`encounterLabel + "\" may return again next round."` — no opening quote), not an actual
`Repercussion`/trait/anything persisted.

The game's **real** "an encounter with no strong resolution carries forward" mechanic lives
elsewhere entirely: see **`.PLAYER_LIFECYCLE.md`, "Prequel stories — round 2's real callback
mechanic"**. It's driven by `CollaborativeTextHelper.getOutcomeTypes`'s `WHAT_HAPPENS_HERE` branch
for `roundNumber > 1`, not by any `RepercussionType`.

## Wire Format: TraitType & RepercussionType

`TraitType` (`model/TraitType.java`) and `RepercussionType` (`model/RepercussionType.java`) are both
annotated `@JsonFormat(shape = JsonFormat.Shape.OBJECT)`, so **any field typed as the enum itself**
(not a DTO that copies its fields) serializes as an object, not a bare string:

```json
{"name": "Trait", "color": "#0288d1"}
```

`Trait.traitType` (`model/Trait.java`) is the one model field with this shape today — `GET /player`
and `GET /player/authorId` return `Player.traits[].traitType` as `{name, color}`. The
`GET /trait-types` endpoint (`AdventureMapController`) also returns `TraitType.values()` directly, so
it now returns `TraitType[]` objects rather than plain enum-name strings — the game-client's
adventure-map-form trait-type picker and the player-client's `trait-badges` component both consume
`traitType.name` / `traitType.color` directly instead of hardcoding badge colors from a switch
statement. `RepercussionType` is never used as a direct field type anywhere today (`Repercussion.
repercussionType` is a plain `String`, and `RepercussionTypeOption` copies the fields into a DTO), so
its `@JsonFormat` is inert until something serializes the enum directly — added for symmetry with
`TraitType` and to avoid the same trap if that changes.

Both enums also carry a custom `@JsonCreator` (`fromJson(JsonNode)`) so **deserialization** accepts
either shape: the legacy bare string (matched case-insensitively against the Java constant name, e.g.
`"STANDARD"`, or the display `name` field, e.g. `"Trait"`), or the full `{name, color}` object emitted
by the new serializer. This keeps old test fixtures and any client still sending a plain string
working, while allowing round-tripping the richer object shape. Without the custom creator, Jackson's
default enum deserializer cannot read the `{name, color}` object back (`shape = OBJECT` only affects
serialization by default) and throws `MismatchedInputException`.

If you add a new `TraitType` or `RepercussionType` constant, no extra work is needed for this — the
custom creator matches on any constant automatically. If you add a new enum field that should carry
similar display metadata (name/color) directly on a model, apply the same two annotations together;
using `@JsonFormat(shape = OBJECT)` alone without the matching `@JsonCreator` breaks read-back of the
object shape.

## Data Flow

### 1 — Class selection

`GET /player/classes` → streams all `PlayerClass` enum values → serialized as `PlayerClassOption[]`
→ player picks one → stored on `Player.playerClass`.

### 2 — What repercussions are available to this player

`GET /collaborativeText/repercussionTypes?gameCode=X&authorId=Y`
→ `CollaborativeTextHelper.getPlayerRepercussionTypes`
→ reads `player.getPlayerClass().getRepercussionTypes()` (list of type name strings)
→ returns matching `RepercussionTypeOption[]`
→ player-client `repercussion-toggle` renders only these options.

### 3 — Attaching a repercussion to an addition

When a player makes an addition (`submitTextAddition`), the `TextAddition` may carry a
`Repercussion` object with `repercussionType` (enum name) and `repercussionSubmission` (the
trait/title text the player typed).

### 4 — Repercussion resolution on winner calculation

Repercussions are only ever resolved into real effects when `MAKE_OUTCOME_CHOICE_VOTING` picks a
winning `OutcomeFork` (`CollaborativeTextHelper.handleMakeOutcomeChoices`) — **not** at
`HOW_DOES_THIS_RESOLVE` time, when a fork is merely created. The winning fork's repercussions are
scanned from its `TextSubmission`'s **full addition chain**, not just the addition that "won" —
every `TextAddition` in that chain with a non-empty `Repercussion` contributes one. This matters
because of how forks form (see `.OUTCOMES.md`, "How a second `OutcomeFork` actually forms"): a
player can branch an addition with a repercussion directly onto another player's addition (chaining,
not sibling-branching), and if that chain ends up the winning fork, **all** the repercussions along
it apply together — e.g. a Scribe's `TRAIT` grant chained under a Bard's `ALL_PLAYERS` addition (or
vice versa) resolves as one combined effect, not two separate ones.

Once collected, `handleRepercussions` fires:

```
repercussions present?
  │
  ├── TRAIT, TITLE, or DESTINY → handleNewTraitRepercussions
  │     applies Trait objects to players in story.playerIds ∪ story.partnerIds
  │
  ├── COMPANION → adds a Trait to those same players, typed COMPANION.
  │     Label is ALWAYS Story.encounterLabel.encounterLabel - the server ignores whatever
  │     text was submitted as Repercussion.repercussionSubmission for this type entirely
  │     (CollaborativeTextHelper.java: `new Trait(story.getEncounterLabel().getEncounterLabel(),
  │     TraitType.COMPANION)`). The real player-client still sends the story's own encounter
  │     label as repercussionSubmission anyway (collaborative-text.component.ts,
  │     onRepercussionChange) - match that when scripting a Companion submission by hand, even
  │     though the server doesn't strictly need it.
  │
  └── ALL_PLAYERS → handleSpread
        re-applies whichever Trait objects were built above (TRAIT/TITLE/DESTINY/COMPANION,
        from repercussions on the SAME winning fork's addition chain) to every player at the
        SAME location as the story (getPlayersAtStoryLocation, excluding story.playerIds/
        partnerIds), not story.playerIds/partnerIds and not every player in the game - this was
        changed from game-wide to location-scoped; verified via FullGameSequelLocationScopeTest
        (src/integrationTest). ALL_PLAYERS alone, with no other repercussion in the chain, has
        nothing to spread - handleSpread just records a display message in that case; no Trait
        is created or applied to anyone (but see .PLAYER_LIFECYCLE.md, "Prequel stories", for
        what an ALL_PLAYERS-alone resolution enables in round 2).
```

The "no repercussions AND roundNumber < 2 → auto-generate a default repercussion" block that used
to be documented here does not actually run — see "SEQUEL is unused" above. Don't rely on it.

### 5 — Traits on Player

Both `TRAIT` and `TITLE` repercussions become `Trait` objects appended to `Player.traits`.
`TraitType.TITLE` entries are rendered in `Player.getDisplayName()` (appended after a comma).
`TraitType.COMPANION` entries appear as companion badges in the player-client UI.

---

## Where Each Class Shows Up in the UI

- **Scribe / Herald**: `repercussion-toggle` shows a text input for the trait/title value
  (`label` field = "Add player trait" / "Add title").
- **Bard**: toggle shows the spread description; no text input needed (`label` = `""`).
- **Fabulist**: toggle shows the companion description; the encounter label is used automatically
  as the companion name (`label` = `""`).
