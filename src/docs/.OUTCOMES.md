OutcomeType Flow to Story Element Documentation (Streamlined Mode)

General Overview: The backend for nowhere is organized primarily in terms of text submissions and outcome types. 
Players submit TextAddition objects in CollaborativeTextHelper.submitTextAddition which are then converted into 
various story elements in the calculateWinningSubmission. Each time the game moves to another collaborative
writing phase, players are assigned text written by others which the frontend retrieves by utilizing
CollaborativeTextHelper.getOutcomeTypes. When an author submits a new TextAddition, it includes the outcomeType
they chose to indicate what their TextAddition was building upon.

Phase: LOCATION_VOTING  [locationVoting flag only]

Initialization (initializeLocationVoting):
- Called once on entering LOCATION_VOTING from PREAMBLE (NOT re-called in round 2).
- In round 0: filters to locations where startingLocation == true.
- In rounds 1+: filters to locations where startingLocation == false.
- Randomly selects N locations (N = player count) from the filtered set.
- Creates one TextSubmission per selected location in the LOCATION_VOTING phase.
- In round 2, clearStoryWritingPhases clears votes but preserves submissions so the same
  location pool is reused without re-initialization.

getOutcomeTypes: N/A - players vote directly on the pre-populated TextSubmissions

Handler: handleLocationVoting
- Reads each player's vote (submissionId = locationId they voted for).
- Sets Player.selectedLocationId from the winning vote.

Phase: SET_ENCOUNTERS

locationVoting flag OFF:
  getOutcomeTypes: Not applicable - no outcomeTypes used
  Handler: addAllSubmissionsToAdventureMap

  getOutcomeTypes:

  - Assigns one location per player using offset: submissions[(playerIndex + 1) % N].
  - Player at index i writes encounter labels for the location at index (i+1) % N (never their own).

  - OutcomeType.label = Location.label (stored as TextSubmission.currentText)
  Handler: addAllSubmissionsToAdventureMap (same as non-voting path)

Phase: WHAT_HAPPENS_HERE

**`locationVoting` feature flag is ON in production** (`GET /featureFlags/value?flagName=locationVoting`
→ `true` as of 2026-08). The flat/unwrapped shape described below (Round 1: flat EncounterLabel
list; Round > 1: filtered flat list) is what runs when the flag is OFF — confirm the live flag value
before relying on it, since the ACTUAL live behavior is the wrapped shape documented right after it.

getOutcomeTypes (Round 1, flag OFF):
- Returns all EncounterLabel objects from AdventureMap
- OutcomeType.id = EncounterLabel.encounterId
- OutcomeType.label = EncounterLabel.encounterLabel

getOutcomeTypes (Round > 1, flag OFF):
- Returns filtered EncounterLabels (excluding already-used ones)
- OutcomeType.clarifier = assigned Story.storyId (for branching)

getOutcomeTypes (flag ON — live behavior, `distributeEncounterLabelsByLocation` /
`buildLocationWrappedOutcomeTypes`, `CollaborativeTextHelper.java`):
- Returns a **single wrapping parent** `OutcomeType` per player, not a flat list:
  `OutcomeType.id`/`label` = the player's assigned `Location`'s id/label; `OutcomeType.subTypes[]` =
  the encounter labels at that location, one per `EncounterLabel` (`subType.id` = `encounterId`,
  `subType.label` = `encounterLabel`). Always at least 2 subTypes — padded with random pre-canned
  encounter labels if the real ones written for that location number fewer than 2.
- A player submitting must therefore send `outcomeTypeWithLabel` as the **parent, narrowed to the
  one chosen subType** — `{ id: parent.id, label: parent.label, clarifier, subTypes: [chosenChild] }`
  — not the bare child alone. `CollaborativeTextHelper.calculateWinnersFromAdditions`'s
  `WHAT_HAPPENS_HERE` branch (under this flag) only counts submissions whose `outcomeTypeWithLabel`
  has a **non-empty `subTypes`**; a submission that flattens to the child loses that wrapper and is
  silently excluded from winner calculation — no error, the round-1 story for that encounter just
  never gets created (`updateGameSessionWithWinningSubmissions` is only invoked when the winners
  list is non-empty). Root-caused 2026-08-09 chasing exactly this symptom against the live backend;
  see the real player-client's `onSelectSubType` (`nowhere-player-client/src/collaborative-text/
  collaborative-text.component.ts`) for the canonical construction of this shape.
- Round > 1 additionally **prepends a "prequel story" subType** (`clarifier` = the original round-1
  `storyId`) to the wrapper, if the requesting player authored a round-1 story that's `visited` and
  whose winning fork carried no repercussion other than possibly a lone `ALL_PLAYERS` — see
  `.PLAYER_LIFECYCLE.md`, "Prequel stories — round 2's real callback mechanic" for the full
  eligibility rule and why this (not `RepercussionType.SEQUEL`) is the real "unresolved encounter
  carries forward" mechanic.

Phase: HOW_DOES_THIS_RESOLVE / HOW_DOES_THIS_RESOLVE_AGAIN

getOutcomeTypes:
- Returns single OutcomeType per player with subTypes array
- OutcomeType.id = Story.storyId (parent)
- OutcomeType.label = Story.prompt
- OutcomeType.clarifier = from distributed story (if set)
- OutcomeType.subTypes[] = WHAT_CAN_WE_TRY submissions related to story:
    - subType.id = TextSubmission.submissionId
    - subType.label = TextSubmission.currentText (the option text)
  If there are no related WHAT_CAN_WE_TRY submissions, subTypes are instead the pre-canned options
  + "use trait: X" options (buildTraitSubTypes) + team-up options
  (getPlayerAtTheSameLocationOutcomeTypes):
    - subType.id = Player.authorId, subType.label = "Team up with <displayName>"
    - One per player whose selectedLocationId matches the **story owner's** (Story.playerId), not
      the writer's, excluding the owner. The writer is included if they share that location.
    - The id becomes Option.optionId, and later Story.selectedOptionId. That's how
      handleRepercussions spots a team-up (see .PLAYER_LIFECYCLE.md, "Relationship traits").

The handler also removes the matched WHAT_CAN_WE_TRY submission and initializes MAKE_CHOICE_VOTING.

How a second `OutcomeFork` actually forms (confirmed 2026-08-09/10, see
`nowhere_java/src/integrationTest/README.md` for the full investigation): it is **not** two
independent root submissions targeting the same `optionId` — that was an early, wrong theory.
- The naturally-assigned player submits a **root** `TextSubmission` (`submissionId: null` →
  `CollaborativeTextHelper.createNewSubmission`).
- `GET /collaborativeText/available` (`CollaborativeTextPhase.getAvailableSubmissionsForPlayer`)
  surfaces that root to **other** players — never its own author, never whoever was last to add to
  it — as something they can branch onto.
- A different player branches onto it (`POST /collaborativeText` with `submissionId` set to the
  root's id → `CollaborativeTextHelper.createBranchedSubmission`), which copies the root's
  `outcomeTypeWithLabel` so the branch still targets the same option, and its `additions` starts as
  the root's own additions plus the new one.
- A **second, different** player branching directly off the **same root** (a sibling of the first
  branch, not a child of it) produces two independent leaf submissions under one root.
- `CollaborativeTextPhase.getSubmissionsWithoutParentSubmissions()` — the function that decides
  `HOW_DOES_THIS_RESOLVE`'s "winners" — excludes any submission referenced as another submission's
  parent. The root is now excluded (both siblings reference it); both siblings are returned as
  winners. `handleHowDoesThisResolve` turns the first winner referencing a given `optionId` into a
  new `Option` + one `OutcomeFork`; every subsequent winner for that same `optionId` appends another
  `OutcomeFork` to it. Only once an `Option` has 2+ forks does `GameSessionHelper` skip its
  single-fork auto-select and run a real `MAKE_OUTCOME_CHOICE_VOTING` vote (see below).
- Branching a **chain** instead (second player branches onto the *first branch*, not onto the root)
  produces one fork whose addition history carries every repercussion in the chain — see
  `.CLASSES.md`, "Repercussion resolution on winner calculation".

Phase: MAKE_OUTCOME_CHOICE_VOTING

getOutcomeTypes: N/A - players vote directly via GET /collaborativeText/voting, same as
LOCATION_VOTING. `initializeMakeOutcomeChoiceVotingPhase` seeds the candidates from
`story.getSelectedOption().getOutcomeForks()` — **only the `Option` that just won**
`MAKE_CHOICE_VOTING`, never a losing option's forks, so a fork attached to an option that didn't win
`MAKE_CHOICE_VOTING` is persisted but never gets a chance to resolve into a real effect.

If the selected option has exactly one `OutcomeFork`, `GameSessionHelper` skips voting and
auto-selects it. With 2+, real voting happens and `submissionId` = the fork's `TextSubmission.
submissionId`.

Handler: handleMakeOutcomeChoices
- `submission.submissionId` → `Option.selectedForkId`
- `submission.currentText` → `Option.successText`
- This is also where `Repercussion`s actually resolve into `Trait`s on players — read from the
  winning fork's full addition chain, not just its final addition. See `.CLASSES.md`, "Repercussion
  resolution on winner calculation" and `.PLAYER_LIFECYCLE.md`'s `MAKE_OUTCOME_CHOICE_VOTING`
  section for the full mechanic.

Notes on new phases:
- DEFINING_TRAITS_VOTING: Each player sees their own traits as OutcomeTypes. Player submits ONE
  TextSubmission where outcomeTypeWithLabel = selected DEFINING trait and subTypes[0] = selected
  PRICE trait. handleDefiningTraitsInternal reads these and writes DefiningTrait objects to
  Player.definingTraits with type="DEFINING" and type="PRICE".
- WRITE_EPILOGUES (updated): subTypes are now DefiningTrait entries (not visited stories).
  Epilogue author selects a defining trait as context. TextSubmission.outcomeType = "DESTINY_ACHIEVED"
  if the author marks destiny as achieved; Ending.didWeSucceed is set accordingly.
- Round 0 (tutorial): SET_ENCOUNTERS intercepts when roundNumber==0, calls handleRoundZeroBoard
  which populates GameBoard from location.startingStories instead of player submissions. No writing
  phases occur in round 0. DESTINY traits are awarded via the normal handleRepercussions path when
  MAKE_OUTCOME_CHOICE_VOTING resolves (single OutcomeFork auto-selects).
- The Summary Table's WHAT_HAPPENS_HERE row (subTypes = N/A) reflects the `locationVoting`-flag-OFF
  shape only. Under the live flag-ON behavior, subTypes is populated (the location-wrapped encounter
  choices, plus a round>1 prequel entry) — see the full WHAT_HAPPENS_HERE section above.
- MAKE_OUTCOME_CHOICE_VOTING isn't in the Summary Table (it's a pure voting phase like
  LOCATION_VOTING/MAKE_CHOICE_VOTING, not an outcomeType-distribution phase) — see its own section
  above.
